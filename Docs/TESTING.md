# Wing it! — 테스트 및 검증 기준

> **문서 상태:** 초기 검증 절차 초안  
> **적용 범위:** Wing it! Unity 프로젝트의 코드·씬·프리팹·설정 변경과 첫 플레이 가능 프로토타입  
> **관련 문서:** [게임 기획서](GDD.md) · [개발 로드맵](ROADMAP.md) · [에이전트 지침](../AGENTS.md)
>
> **중요:** 이 문서는 *어떻게 검증할지* 정의한다. 문서에 시험 항목이 있다는 사실만으로 해당 기능이 구현되었거나 테스트를 통과한 것은 아니다. 현재 프로젝트의 실제 검증 결과는 별도로 확인해야 한다.

## 1. 목적과 기본 원칙

이 문서는 AI 에이전트와 개발자가 **무엇을 확인해야 작업을 완료했다고 판단할 수 있는지** 정의한다. 오류를 빠르게 재현하고 원인을 추적하며, 수정으로 인해 기존 기능이 망가지지 않도록 하는 것이 목표다.

- **수정 범위에 맞게 검증한다.** 모든 작업마다 전체 게임을 반복 검사하지 않고 변경에 영향받는 기능을 우선 확인한다.
- **근거가 있는 결과만 보고한다.** 코드 검토, 컴파일, Play Mode 실행, 실제 조작 결과를 서로 다른 검증으로 취급한다.
- **컴파일 성공 ≠ 기능 정상 작동.** 에디터에서 플레이하거나 실제 동작을 확인하지 않았다면 기능 검증을 완료했다고 표시하지 않는다.
- **도구의 한계를 숨기지 않는다.** Unity MCP나 테스트 실행 기능이 없는 경우 수행하지 못한 항목을 `미검증`으로 남긴다.
- **기획상 미정인 수치는 확정 기준으로 취급하지 않는다.** 테스트용 임시값은 임시값으로 표시하고, 체감 평가는 별도로 기록한다.
- **결과와 원인 설명은 한국어로 작성한다.** 오류·로그·API명·파일 경로 등 기술 식별자의 원문은 유지한다.

## 2. 검증 상태와 완료 판정

### 2.1 검증 결과

| 결과 | 의미 | 기록 원칙 |
| --- | --- | --- |
| `성공` | 명시한 조건을 실제로 확인했으며 기대 결과와 일치함 | 수행 방법과 확인 근거를 남김 |
| `실패` | 테스트를 수행했고 기대 결과를 충족하지 못함 | 실제 결과, 재현 방법, 오류 정보를 남김 |
| `미검증` | 실행하지 못했거나 결과를 확인할 증거가 부족함 | 수행하지 못한 이유와 필요한 다음 확인을 남김 |

> `미검증`은 `성공`도 `실패`도 아니다. 파일 존재, 코드 작성, AI의 추측만으로 성공 처리하지 않는다.

### 2.2 작업 완료 기준

- **조사·문서 작업:** 요청 범위의 내용을 확인하고 변경·미확인 사항을 보고하면 종료할 수 있다. 실행 검증이 필요하지 않은 경우 불필요한 Play Mode 테스트를 강제하지 않는다.
- **코드·에셋 수정:** 관련 정적 검토를 수행하고, 가능한 경우 컴파일과 관련 콘솔 상태를 확인한다. 실제 동작이 중요한 수정은 기능 테스트까지 확인해야 해당 기능을 `완료`로 보고할 수 있다.
- **기능 구현:** 기대 동작과 관련 회귀 항목이 검증되어야 `완료`로 처리한다. 필수 검증이 남아 있으면 `검증 대기` 또는 `미검증` 상태로 보고한다.
- **로드맵 단계 완료:** 해당 단계의 완료 조건 및 필수 검증 항목을 충족해야 한다. 일부 체크박스가 완료됐다는 이유만으로 단계 전체를 완료 처리하지 않는다.
- **재미·조작감 판정:** 기술적 정상 작동과 별도로 실제 플레이를 통해 평가한다. 자동 테스트 통과만으로 재미를 판정하지 않는다.

### 2.3 테스트 실행 정보 기록

테스트 결과를 재현할 수 있도록 기능 테스트를 실행한 경우 다음 정보를 결과와 함께 기록한다. 확인할 수 없는 값은 추측하지 말고 `미확인`으로 적는다.

- 실행 날짜 (`YYYY-MM-DD`)
- Unity 버전
- 테스트한 씬
- 실행 환경: Editor/Play Mode 또는 빌드 실행, 대상 플랫폼(해당하는 경우)
- 테스트 방식: 직접 조작, 자동화 테스트, 정적 검토 등
- 필요한 경우 테스트에 사용한 임시 설정이나 재현 조건

문서 검토처럼 실행 환경이 관련 없는 작업에는 해당 정보를 형식적으로 채우지 않는다.
## 3. 변경 후 기본 검증 절차

아래 순서는 코드 또는 Unity 에셋을 수정했을 때 사용하는 기본 흐름이다. 변경 성격에 따라 필요한 항목을 선택한다.

### 3.1 변경 전 확인

1. 수정 대상 코드·씬·프리팹·설정과 관련 참조를 확인한다.
2. 기대 동작과 기존 동작을 구분한다. 기획이 미정이라면 테스트 목적의 가정임을 기록한다.
3. 현재 오류, 사용자가 수정 중인 파일, 영향받는 기능을 확인한다.
4. 다른 작업 내용을 임의로 삭제하거나 덮어쓰지 않는다.

### 3.2 정적 검토

- 수정 코드의 문법, 변수 초기화, 참조와 조건 분기를 점검한다.
- `NullReferenceException` 가능성이 있는 Inspector 연결, 컴포넌트 조회와 씬 오브젝트를 살핀다.
- 입력 처리, 물리 처리와 프레임 단위 처리의 위치가 의도에 맞는지 확인한다.
- 씬·프리팹을 수정했다면 `.meta` 및 GUID, 오브젝트 참조, 태그·레이어, Animator 파라미터, Input Action 연결을 점검한다.
- 변경 범위 밖에 예상치 못한 수정이 있는지 확인한다.

**판정 주의:** 정적 검토 성공은 실행·컴파일 성공을 보증하지 않는다.

### 3.3 컴파일 및 콘솔 확인

가능하면 Unity 에디터에서 다음을 확인한다.

1. 변경 사항이 반영된 뒤 스크립트 컴파일 또는 에셋 임포트가 끝났는지 확인한다.
2. Unity Console의 `Error`와 관련 예외를 확인한다.
3. 오류가 있다면 **발생 파일·위치·메시지 원문**을 기록하고, 새 변경과 관련된 오류인지 구분한다.
4. 수정한 오류는 재컴파일하여 다시 확인한다.
5. `Warning`은 무조건 실패로 취급하지 않되, 수정 기능에 영향을 주는 경고는 확인한다.

**성공 기준:** 변경과 관련된 컴파일 오류가 없고, 확인 범위에서 실행을 막는 신규 오류가 없다. 기존에 있던 별도 오류는 구분해 보고한다.

### 3.4 기능 검증 — Play Mode

- 변경한 기능을 실행할 수 있는 **적절한 씬**을 열고 Play Mode를 실행한다.
- 입력, 움직임, 충돌, 공격 등 해당 기능을 실제 조건에서 재현한다.
- 기대 결과와 실제 결과를 비교한다.
- 시작 직후, 반복 입력, 경계 상황 등 주요 예외 상황을 확인한다.
- 실행 중 새 오류가 발생했는지 확인한다.

**주의:** Play Mode를 열었다는 사실만으로 기능 검증이 끝난 것은 아니다. 실제 동작을 관찰하거나 신뢰할 수 있는 실행 결과를 확인해야 한다.

### 3.5 회귀 검증

수정과 직접 연결된 **기존 기능**도 최소한으로 재확인한다.

예시:

| 수정 항목 | 함께 확인할 기존 동작 |
| --- | --- |
| 상승 입력 | 기본 전진, 중력, 지면·천장 충돌 |
| 고속 활공 | 순간 상승, 활공 종료 후 하강, 속도 복귀 |
| 사격 | 이동 중 입력, 조준 방향, 피격 판정 |
| 적 또는 장애물 | 기존 이동·회피, 충돌 처리, 플레이 진행 |
| 카메라 또는 씬 | 플레이어 표시, 조준 좌표, 주요 오브젝트 참조 |

### 3.6 실패 처리와 재검증

1. 오류를 재현할 수 있는 입력·조건을 정리한다.
2. 관찰한 사실과 추정 원인을 분리한다.
3. 요청 범위 안에서 수정할 수 있는 문제라면 원인을 수정한다.
4. 같은 테스트를 다시 실행해 해결 여부를 확인한다.
5. 관련 기존 기능의 회귀 검증도 수행한다.
6. 해결하지 못했다면 `실패` 또는 `미검증` 상태와 남은 위험을 보고한다.

반복해서 실패하는 경우 원인을 확인하지 않은 채 임시 우회 코드를 누적하거나, 성공했다고 보고하지 않는다.

## 4. 첫 번째 프로토타입의 기능별 검증

아래 항목은 [GDD](GDD.md)의 핵심 방향과 [ROADMAP](ROADMAP.md)의 1~4단계를 기준으로 한 **예정된 검증 항목**이다. 아직 수행·성공한 테스트 목록이 아니다. 물리 수치, 전환 시간, 조준 각도 등 미확정 사항은 임시값으로 시험하고 결과에 기록한다.

| 대상 | 시험 방법 | 기대 결과 | 주요 추가 확인 |
| --- | --- | --- | --- |
| 자동 전진 | 테스트 씬에서 입력 없이 시작 | 오른쪽으로 전진하는 흐름이 유지됨 | 지상·공중 전환 중 진행 유지 |
| 지상 이동·중력 | 지면에서 이동하고 공중에서 입력을 멈춤 | 지상 이동이 가능하며 공중에서 하강함 | 지면 관통·공중 정지 여부 |
| 일반 점프 | `Space`를 짧게 누른 뒤 반복해서 놓음 | 누르는 순간에는 상승하지 않고, 손을 뗄 때마다 설정한 일반 점프 높이로 상승함 | 연속 입력·지면 근처·천장 근처 |
| 고속 활공 | `Space`를 설정 시간 이상 누른 뒤 놓음 | 전환 시 설정한 낮은 높이로 한 번 상승하고 하강 완화·전진 가속이 나타남. 손을 뗄 때 추가 상승 없이 기본 이동으로 복귀함 | 두 점프 높이 비교·구분 시간 경계·해제 후 낙하 |
| 조준 | 플레이 중 마우스를 플레이어 앞·뒤·위·아래로 움직임 | 총구가 마우스를 향하되 횡스크롤 기준 전방 180도 밖으로 돌아가지 않음 | 뒤쪽 위·아래에서 수직 경계로 제한, 화면 경계·공중 상태 |
| 기본 사격 | 앞쪽과 뒤쪽을 가리킨 채 왼쪽 버튼을 클릭하고 길게 누름 | 전방 범위로 탄환이 발사되고, 누르는 동안 설정 간격으로 반복 발사되며 손을 떼면 멈춤 | 이동·비행 중 공격, 짧은 클릭, 탄환 수명·충돌 |
| 피격 판정 | 시험용 적을 탄환으로 맞힘 | 맞은 적이 제거되고 탄환도 사라짐 | 빗맞힘·중복 피격 |
| 지형·장애물 | 지상 장애물에 접촉하고, 점프 또는 낮은 경로로 지상·공중 장애물을 피함 | 접촉 시 플레이어가 잠깐 붉어졌다가 원래 색으로 돌아오고, 피한 경우 피격 표시가 없음 | 중복 접촉·연속 피격·지면 관통·공중 경계 |
| 기본 적 | 일반 적 프리팹 인스턴스와 조우 | 화면 안에서 가까운 플레이어에게 접근·발사하고, 피격 시 제거됨 | 프리팹 연결·플레이어 참조·공격 간격 |
| 화면 밖 일반 적 | 적이 화면에 나타나기 전과 나타난 뒤 화면 밖으로 나간 상태를 확인 | 처음부터 화면 밖인 적은 대기하고, 한 번 나타난 적은 화면 밖에서 새 공격·접근을 멈추며 5초 뒤 제거됨 | 5초 전후·재진입 시 타이머 초기화·기존 발사체 |
| 짧은 테스트 구간 | 시작부터 끝까지 연속 플레이 | 전진·상승·활공·사격·회피를 한 흐름으로 경험함 | 진행 불능, 반복 실행 |

**판정 방식:** 기능별 세부 요구가 확정되면 기대 결과를 더 구체화한다. 현재 기획에 없는 체력·사망·재시작·아이템·증강·보스 규칙을 이 표만으로 확정하지 않는다.

## 5. 조작감과 재미 평가

기술적 테스트와 별개로 짧은 구간을 직접 플레이하면서 아래 질문을 확인한다.

1. 자동 전진 속도와 고도 조절을 이해하기 쉬운가?
2. 반복 상승과 고속 활공이 서로 다른 선택으로 느껴지는가?
3. 이동하면서 마우스로 조준·사격할 때 부담이 지나치지 않은가?
4. 장애물과 적이 의미 있는 회피·공격 결정을 만들고 있는가?
5. 짧은 구간을 다시 플레이하고 싶은가? 가장 불편한 점은 무엇인가?

평가는 `유지 / 조정 후 재검증 / 핵심 방식 재검토` 중 하나로 정리하고, **관찰한 문제와 판단 이유**를 함께 남긴다. 초기에는 임의의 점수나 통과율을 확정 기준으로 사용하지 않는다.

## 6. Unity MCP 및 자동화 테스트 사용

- Unity MCP가 연결되고 필요한 기능을 제공한다면 씬·오브젝트·컴포넌트 상태, 콘솔, 테스트 실행 가능 여부를 확인하는 데 활용한다.
- **도구가 실제로 제공하는 기능만 사용한다.** MCP 연결만으로 화면 조작·Play Mode 관찰·자동 테스트가 모두 가능하다고 가정하지 않는다.
- Unity Test Framework의 Edit Mode / Play Mode 테스트는 해당 기능을 자동으로 검증할 필요가 생겼을 때 도입한다. 현재 자동 테스트 파일이 존재한다고 가정하지 않는다.
- 자동화할 수 있는 로직은 테스트 코드로 검증할 수 있지만, 시각적 연출·조작감·재미는 별도 플레이 확인이 필요할 수 있다.
- Unity 에디터나 MCP를 사용할 수 없는 환경이라면 파일 검사와 정적 분석 범위를 설명하고, 실행·기능 테스트는 `미검증`으로 남긴다.

## 7. 검증 결과 보고 형식

코드·에셋 변경 후에는 작업 규모에 맞춰 아래 정보를 한국어로 보고한다. 모든 항목을 무조건 길게 작성할 필요는 없지만 **어떤 검증을 했는지**는 구분해야 한다.

```text
[작업 내용]
- 수정 파일:
- 변경 내용 및 이유:

[테스트 맥락 — 실행 검증을 한 경우]
- 날짜:
- Unity 버전:
- 테스트 씬:
- 실행 환경 / 플랫폼:
- 테스트 방식:
- 재현 조건 또는 임시 설정(해당하는 경우):

[검증 결과]
- 정적 검토: 성공 / 실패 / 미검증 — 근거
- 컴파일·콘솔: 성공 / 실패 / 미검증 — 근거
- 기능 테스트: 성공 / 실패 / 미검증 — 근거
- 회귀 테스트: 성공 / 실패 / 미검증 — 근거

[문제 및 후속 확인]
- 확인된 오류:
- 추정 원인(있는 경우):
- 미검증 항목과 이유:
- 사용자가 직접 확인할 방법(필요한 경우):
```

오류 발생 시 가능하면 오류 메시지 **원문**, 한국어 설명, 발생 위치, 재현 단계, 수정 사항, 재검증 결과를 포함한다. 로그는 필요한 부분만 인용하고 비밀값·개인정보를 남기지 않는다.

## 8. 문서 갱신 기준

- 이 문서는 **재사용할 테스트 절차와 완료 판정 기준**이 변경될 때 갱신한다.
- 기능별 실제 진행 상태는 [`ROADMAP.md`](ROADMAP.md)에 기록한다.
- 합의된 게임 규칙이 바뀌면 [`GDD.md`](GDD.md)를 갱신한다.
- 중요한 기술·설계 결정과 이유는 [`Decisions/`](Decisions/README.md)에 ADR로 기록한다.
- 일회성 콘솔 로그, 모든 테스트 실행 기록과 사소한 오류를 이 문서에 무한히 누적하지 않는다. 필요한 실행 결과는 작업 보고에서 공유한다.
- 새 검증 기준을 추가할 때는 실현 가능한 절차인지, 사용자가 직접 확인해야 하는 항목인지 구분한다.

---

**검증의 핵심은 '작동할 것 같다'가 아니라, 무엇을 실제로 확인했고 무엇이 아직 확인되지 않았는지 분명히 남기는 것이다.**
