# Wing it! — 기술·설계 결정 기록

> **문서 역할:** 중요한 기술·설계 결정(ADR, Architecture Decision Record)의 목차와 관리 기준
>
> **현재 상태:** 기획 전환과 2D 프로젝트 초기화 결정 2건 등록.
>
> **위치:** `Docs/Decisions/README.md`

## 1. 목적

이 폴더는 Wing it! 개발 과정에서 **어떤 결정을 내렸는지, 왜 그 방안을 선택했는지, 어떤 범위에 영향을 주는지**를 남긴다. 시간이 지난 뒤에도 설계 배경을 이해하고, 변경 필요성을 판단할 수 있도록 한다.

- 결정은 개별 Markdown 파일로 기록한다.
- 결정 과정의 근거와 검토한 대안을 함께 남긴다.
- 확정되지 않은 내용은 확정된 사실로 작성하지 않는다.
- 가벼운 코드 수정, 일회성 오류 해결 및 단순한 작업 내역은 ADR로 만들지 않는다.
- 설명과 본문은 한국어로 작성하되 코드 식별자, 경로, API명 등은 원문을 유지한다.

## 3. 어떤 결정을 기록할까?

**기록 대상 예시**

- 캐릭터 및 월드의 이동·충돌 구조처럼 이후 기능 개발에 영향을 주는 설계 선택
- 입력 시스템, 데이터 저장 방식, 씬·시스템 간 통신 구조 등 주요 기술 선택
- 외부 패키지·도구를 채택하거나 기존 방식을 교체하는 결정
- 기존 핵심 설계를 바꾸는 결정과 그 이유

**보통 기록하지 않는 내용**

- 변수 이름 변경, 사소한 코드 정리
- 일회성 버그 수정과 임시 디버그 로그
- 아직 비교·검토하지 않은 아이디어
- 단순한 진행 현황이나 테스트 실행 결과

게임의 **무엇을 만들 것인지**는 `../GDD.md`, **언제·어디까지 진행했는지**는 `../ROADMAP.md`, **어떻게 검증하는지**는 `../TESTING.md`에서 관리한다.

## 4. 파일명과 번호 규칙

- 파일명은 `0001-player-movement.md`처럼 **4자리 일련번호 + 짧은 주제**를 사용한다.
- 새 ADR 작성 전 폴더의 4자리 번호 파일을 확인한다. 기존 ADR 파일과 빈 자리표시자 파일이 있으면 번호를 중복 사용하지 않는다. 이름이 주제와 맞는 빈 파일이 있으면 그 파일을 채우고, 새 파일이 필요하면 가장 큰 기존 번호 다음 번호를 사용한다.
- 파일명에 사용하는 기술적 키워드는 필요하면 영어로 작성할 수 있지만, 문서의 제목과 설명은 한국어로 작성한다.
- 한 파일에는 원칙적으로 하나의 중요한 결정을 기록한다.
- 삭제나 번호 재사용으로 기존 결정 이력이 끊기지 않게 한다.

## 5. 결정 상태

| 상태 | 의미 |
| --- | --- |
| `제안` | 대안을 검토하고 있으나 확정되지 않음 |
| `확정` | 현재 채택한 결정 |
| `대체됨` | 새로운 ADR에 의해 다른 결정으로 변경됨 |
| `폐기` | 채택하지 않거나 더 이상 적용하지 않기로 함 |

## 6. 개별 ADR 작성 양식

새 결정을 기록할 때 다음 내용을 새 파일에 복사해 사용한다.

```markdown
# ADR-0001: 결정 제목

- 날짜: YYYY-MM-DD
- 상태: 제안
- 관련 시스템: 해당 시스템 이름
- 관련 문서: (필요한 경우 링크)

## 배경과 문제

어떤 상황과 문제가 있어 이 결정을 검토하는지 적는다.

## 검토한 대안

1. 대안 A: 장점과 단점
2. 대안 B: 장점과 단점

## 선택한 방안

채택한 방법을 적는다. 아직 미확정이라면 '검토 중'으로 표시한다.

## 결정 이유

다른 대안과 비교해 선택한 근거를 적는다.

## 영향 범위

- 관련 시스템과 파일
- 예상되는 장점과 위험
- 마이그레이션이나 후속 작업(필요한 경우)

## 검증 상태

- 검증 방법:
- 결과: 성공 / 실패 / 미검증
- 확인 근거 또는 남은 확인 사항:

## 관련 결정

대체하거나 참조하는 ADR이 있으면 링크를 적는다.
```

위 양식은 **템플릿**이며, 실제 결정이 확정되기 전에는 기록 내용을 임의로 채우지 않는다.

## 7. 변경 및 대체 관리

1. 기존 결정의 배경이나 결론을 조용히 덮어쓰지 않는다.
2. 중요한 설계 변경은 새 번호의 ADR로 작성한다.
3. 이전 ADR의 상태를 `대체됨`으로 변경하고 새 ADR을 연결한다.
4. 새 ADR에도 이전 결정으로의 링크와 변경 이유를 기록한다.
5. 이 README의 결정 목록을 갱신한다.

오탈자나 링크 수정 같은 편집은 새 ADR을 만들 필요가 없다.
